## ASR 性能排查（用户反馈「玩 VRChat 时半天才识别出来」）
- 现状：`asr.json` provider=cpu，pip 装的 sherpa-onnx 1.13.8 win_amd64 wheel 只带 CPU 版 onnxruntime.dll（17MB，无 onnxruntime_providers_*.dll），**确认纯 CPU**。
- 机器：R7 9700X（8C/8T）+ RX 7900 XTX + RTX 4090。
- 实测 Qwen3-ASR 0.6B int8、num_threads=6：空闲 RTF≈0.07（10s→0.8s，15s→1.06s）；8 个进程打满 8 线程后 RTF≈0.30（10s→3.0s，15s→3.35s，慢 4 倍）。→ 卡顿根因是 VRChat 抢 CPU，不是模型本身慢。
- 架构问题：前端每 900ms 发一个 chunk，服务端每次都把**整段累积音频重新解码**，单线程 `_model_lock` 串行；解码变慢后队列积压（MAX_QUEUE=5），final 结果被拖到十几秒后。
- GPU 方案：sherpa-onnx 官方 Windows 预编译只有 CUDA（v2.0.1，cuda12/13 + cudnn9），无 DirectML 包；源码有 `SHERPA_ONNX_ENABLE_DIRECTML` 开关（Windows only）+ `provider="directml"`，需自行 VS2022 编译，替换 site-packages/sherpa_onnx/lib 下 DLL 即可，Python 代码不用改。
- 记住：GPU 只解决 compute，final 延迟还有 850ms 停顿判定在等。

## GPU 加速可行性实测（结论：7900 XTX 这条路走不通）
- DXGI 适配器顺序：**0 = RTX 4090，1 = RX 7900 XTX，2 = WARP**。sherpa-onnx 的 DirectML 分支把 `device_id` 硬编码为 0，就算编出来也会跑到 4090 上，必须打补丁改成 1。
- **ROCm 全路径关闭**：① ORT 自 1.23 起已移除 ROCm EP（ROCm 7.0 是最后支持版，之后改用 MIGraphX）；② 所有 ORT ROCm/MIGraphX wheel 只有 manylinux（Linux），Windows 无 wheel；③ sherpa-onnx 的 `provider.cc` 里根本没有 rocm/migraphx 选项，只有 cpu/cuda/coreml/xnnpack/nnapi/trt/directml/spacemit/openvino。
- **DirectML 实测反而更慢**（onnxruntime-directml 1.24.4，decoder.int8 单步解码）：
  - CPU 62 tok/s（16.2 ms/step）
  - DML @7900 XTX（device 1）18 tok/s（55.9 ms/step）→ 慢 3.5 倍
  - DML @4090（device 0）22 tok/s（46.3 ms/step）→ 慢 2.8 倍
  - encoder 也只快 1.2~1.4 倍（1500 tokens：CPU 178ms vs DML 126ms）
  - 原因：模型是 int8 量化 + seq=1 自回归逐 token，GPU 全被 dispatch 开销和反量化吃掉，发挥不出来。
- 好消息：decoder 的 KV cache 是定长 `max_total_len`，只有 batch/seq 动态，所以 DML 不会每 token 重建图——慢不是因为重建。
- 所以「上 GPU」对这个 0.6B int8 自回归模型没有意义；真正的杠杆是**换非自回归模型**（SenseVoice / FunASR-nano，sherpa-onnx 都有 `from_sense_voice` / `from_funasr_nano`）或改架构。SenseVoice 模型包 1.05GB。
- 环境：VS2022 Community + MSVC 14.44 + Win SDK 10.0.19041 齐备，无 cmake/ninja（可 pip 装）；系统装了 CUDA 13.0（有 cublas64_13.dll），但**没有 cuDNN 9**。

## 换框架跑 Qwen3-ASR：llama.cpp 完胜（已实测）
- **llama.cpp 原生支持 Qwen3-ASR**，GGUF 在 `ggml-org/Qwen3-ASR-0.6B-GGUF`（Q8_0 805MB + mmproj Q8_0 214MB），和项目现在用的 0.6B 是同一个模型，识别文本完全一致。
- llama.cpp b12032 官方 Windows 预编译三种后端：`bin-win-vulkan-x64`(38MB)、`bin-win-rocm-10.0-x64`(266MB)、`bin-win-cuda-13.4-x64`(165MB)。
- **Vulkan 版解压即用，实测延迟（llama-server，唯一音频避免 prompt cache 命中）：10s 语音 0.13s、15s 语音 0.14s，decode 470~485 tok/s。** 对比 sherpa-onnx CPU 空闲 0.74/1.02s、VRChat 抢满时 3.03/3.35s。约 7~23 倍提升，且完全不碰 4090。
- **ROCm 版能识别显卡但一推理就崩**：`CUBLAS_STATUS_INVALID_VALUE` @ `hipblasSetStream`。原因：包里只有 `amdhip64_7.dll`/`amd_comgr.dll`，**没有 rocblas/hipblasLt**，必须先装完整 ROCm/HIP SDK。既然 Vulkan 已够快，ROCm 没必要。

## 「点开始没反应」排查结论
- **根因不是代码，是麦克风本身在送纯静音**。用 playwright + 真实设备实测：系统里只有 Pico 串流麦（`PicoStreamingMicrophone` / `Pico Streaming Speaker`），三组约束（`audio:true`、项目的无 DSP 单声道、立体声）峰值全部是 **0.0000**；换成 Chrome 假设备（`--use-fake-device-for-media-stream`）音量条能到 100%，证明采集链路没问题。
- 排查手法（可复用）：playwright `add_init_script` 劫持 `AudioContext` 记录 `state`；独立 HTML + `AnalyserNode.getFloatTimeDomainData` 量峰值；`page.evaluate` 轮询 `#asrMeterFill.style.width` 取最大值（单次采样会撞上静音间隙，误判）。
- 顺带修的三个真问题：① 纯静音被送进模型会幻觉出「嗯。」并写进草稿 → 服务端加 `_is_silent`（峰值 < 5e-4 直接返回空）；② 设备无信号时界面只显示「正在监听」毫无提示 → 前端 4 秒内峰值低于 0.002 就提示具体设备名，且不被「正在识别…」覆盖；③ 父进程被强杀时 llama-server 会残留占 1GB 显存 → 用 Windows Job Object（KILL_ON_JOB_CLOSE）绑定生命周期，已用 `os._exit(0)` 验证子进程被回收。
- 另外给 `start()` 补了 `audioCtx.resume()`（经过多个 await 后创建上下文可能停在 suspended，此时 onaudioprocess 完全不触发，且无任何报错）。
- 调试用的 playwright 及其 714MB 浏览器缓存已全部卸载/删除，venv 回到 90MB。

## 「没说话也一直识别出嗯」——静音幻觉
- 原因：前端每 900ms **无条件**上传分片，静音/环境噪声也会被送去解码，Qwen3-ASR 对空音频会输出「嗯。」这类填充词并渲染成草稿。
- 三层拦截（已实测）：
  1. 前端：`if (currentUtteranceHasAudio || speechRms > SILENT_RMS) enqueue(...)`，纯静音不再上传。门槛特意用 0.002 而非 0.012，避免音量小的用户被卡死。
  2. 服务端 `_activity()`：按 20ms 帧算 RMS，超过噪声底(0.006)的**有效语音时长** < 150ms 直接返回空；另加 peak < 5e-4 的绝对静音短路。
  3. 结果过滤：音量峰值 < 0.06 且结果只是「嗯/啊/呃…」单语气词时丢弃（正常说话音量下不受影响）。
- 实测：真实语音 8s ✓、音量×0.12 的小声说话 ✓（都正常出字）；数字静音、1e-4/5e-3/2e-2 噪声、50ms 短促噪声 → 全部返回空。
- 注意：`_is_silent()` 已被 `_activity()` 取代，别再加回去。
